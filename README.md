## Лабораторна робота №16 — Web Storage API

Портфоліо зберігає вибрані проєкти та тему в `localStorage`, а чернетку навчальної заявки — у `sessionStorage`. У попередніх роботах кошик і зона улюбленого були адаптовані до одного списку `selectedProjects`; тут він також залишається єдиним джерелом стану, без дублювання двох списків.

- `silkov_portfolio_selected_v1` — JSON-масив обраних проєктів. Запис змінюється після вибору/видалення, Drag-and-Drop та очищення. Після успішного формування заявки ключ видаляється.
- `silkov_portfolio_theme` — `light` або `dark`. Якщо вибору немає, використовується системна тема. Короткий скрипт перед CSS застосовує палітру без білого спалаху; тема також відновлюється на сторінках входу та реєстрації.
- `silkov_portfolio_draft_v1` — лише поля `clientName`, `clientPhone`, `clientEmail`, `orderPromo` у сесійному сховищі поточної вкладки. Чернетка автоматично записується при `input`, відновлюється до обчислення підсумку та видаляється після успіху. Паролі зі сторінок входу/реєстрації не зберігаються цим кодом.
- Читання, парсинг і запис захищені `try...catch`. Перевіряються типи, ID, довжини рядків, URL та дублікати. Некоректний JSON власного ключа видаляється; якщо пам’ять заблокована чи переповнена, сайт продовжує працювати в пам’яті сторінки та показує повідомлення.
- Збережені проєкти відображаються ще до завершення Fetch і залишаються доступними для видалення, навіть якщо API недоступне або проєкт більше не входить до перших восьми репозиторіїв.
- `storage` синхронізує список і тему в інших вкладках того самого origin без перезавантаження. Обробник не викликає повторного запису, тому циклу синхронізації немає. Контакти чернетки між окремими вкладками не синхронізуються.
- Очищаються лише власні ключі через `removeItem()`; `localStorage.clear()` не застосовується, щоб не зачепити інші дані того самого origin.

### Відповіді на контрольні питання ЛР №16

1. **localStorage і sessionStorage.** Обидва сховища прив’язані до origin (протокол, хост, порт). `localStorage` спільне для вкладок цього origin і зазвичай переживає закриття браузера, доки його не видалять або браузер не очистить дані. `sessionStorage` додатково ізольоване за вкладкою, переживає перезавантаження та переходи в її межах і належить сесії цієї вкладки. Відновлення сесії браузером може відновити й ці дані, тому це не гарантія безпечного стирання.
2. **Навіщо JSON.stringify().** Web Storage зберігає рядки. `JSON.stringify()` перетворює масив/об’єкт на JSON-рядок, а `JSON.parse()` відновлює структуру. Об’єкт напряму зазвичай перетвориться на `[object Object]`, і початкові поля втратяться.
3. **Квота й QuotaExceededError.** Для Web Storage типово наводять близько 5 MiB для localStorage та 5 MiB для sessionStorage на origin; конкретні обмеження й доступність залежать від браузера та режиму. Запис обгортають у `try...catch`, скорочують обсяг власних даних, видаляють непотрібні власні записи й повідомляють користувача, зберігаючи роботу сторінки. Великі обсяги краще зберігати в IndexedDB.
4. **Чому не можна зберігати паролі чи карткові дані?** localStorage доступне JavaScript цього origin; при XSS зловмисний скрипт може прочитати його. Дані можуть залишитися на спільному пристрої надовго, і сховище саме по собі не дає захисту секретів. sessionStorage також доступне скриптам і не усуває XSS-ризик; обмежений час життя не робить його сейфом.
5. **Коли виникає storage?** Коли інший документ змінює спільну область сховища: для localStorage це інші вкладки/вікна того самого origin. Подія надходить до них, а не до документа-ініціатора: він уже знає про зміну й оновлює свій UI сам. Повторний запис того самого значення не створює зміни; при `clear()` ключ у події дорівнює `null`. Для sessionStorage подія стосується документів зі спільною сесією вкладки, наприклад відповідних iframe, а не незалежних вкладок.

## Лабораторна робота №15 — живий пошук і форма заявки

Завдання адаптоване до портфоліо: пошук працює по назвах репозиторіїв, а в модальному вікні обраного розміщено навчальну форму заявки щодо проєктів. Для демонстрації розрахунку та промокоду кожному обраному проєкту відповідає 100 **умовних одиниць**. Це не ціни послуг і не платіж. Форма явно повідомляє, що дані нікуди не надсилаються.

- Генерацію карток винесено в `renderProjects(projectsToDisplay)`. І первинне завантаження, і пошук викликають цей рендерер.
- Подія `input` нормалізує запит через `trim().toLowerCase()`, а `filter()` та `includes()` шукають у повному масиві `globalStoreProjects`. Є кількість збігів і порожній стан. Пошук не видаляє обране; делеговані кліки та Drag-and-Drop працюють після перемальовування.
- У формі є ім’я/прізвище, телефон, email і необов’язковий промокод. `submit` скасовує стандартну дію через `preventDefault()` та отримує значення через `new FormData(orderForm)`.
- З імені прибираються крайні й повторні пробіли, з телефону — пробіли, дужки й дефіси; email переводиться в нижній регістр, промокод — у верхній.
- Перевіряються щонайменше два слова імені від двох літер, український номер через `/^\+?380\d{9}$/` та формат email. Помилки показуються біля полів, `aria-invalid` оновлюється, фокус переходить до першої помилки.
- `reduce()` рахує кількість і навчальний підсумок; `SALE10` дає 10%. Промокод регістронезалежний, незнайомий код не дає знижки. Суми мають два знаки після коми.
- Після успішної перевірки `map()` формує позиції, створюється JSON із контактами, проєктами, навчальним розрахунком, промокодом та ISO-датою. JSON видно лише в консолі поточного браузера. Обране й форма очищаються, модалка закривається, на сторінці з’являється повідомлення про локальне формування заявки.
- Секрети, серверна відправка, оплата та Web Storage не використовуються. Клієнтська валідація сама по собі не замінює серверної перевірки в реальному сервісі.

### Перевірка ЛР №15

1. У пошуку ввести назву проєкту великими літерами та з пробілами по краях: збіг знаходиться. Невідома назва показує 0 і порожній стан. Очищення пошуку повертає всі картки.
2. Обрати проєкт, сховати його пошуком та відкрити «Обране»: вибір зберігається. Після очищення пошуку перевірити кнопку й перетаскування.
3. Відправити порожню форму: відображаються підказки, сторінка не перезавантажується, вибір не зникає.
4. Ввести `  Тестовий   Користувач `, `+38 (097) 123-45-67`, ` TEST@EXAMPLE.COM ` та ` sale10 `. Для одного проєкту: 100.00 до знижки, 10.00 знижка, 90.00 підсумок.
5. З валідними контактами й порожнім обраним форму не можна завершити. Після успіху JSON містить очищені значення, обране та поля порожні, видиме повідомлення каже, що дані не надсилалися.

### Відповіді на контрольні питання ЛР №15

1. **Навіщо `event.preventDefault()` при submit?** Щоб скасувати стандартне відправлення HTML-форми з переходом/перезавантаженням сторінки. Це дозволяє перевірити дані JavaScript, показати помилки та зберегти поточний масив обраного в пам’яті.
2. **Перевага FormData.** `new FormData(form)` збирає успішні поля форми за їхніми атрибутами `name` без окремого `querySelector()` для кожного. Підтримує однакові імена й файли; поля без `name`, вимкнені поля та непозначені checkbox не включаються. Значення все одно потрібно нормалізувати й перевіряти.
3. **Чому input, а не change?** `input` спрацьовує під час кожної зміни користувачем — введення, вставки або видалення. `change` у текстовому полі зазвичай спрацьовує після підтвердження зміни чи втрати фокусу, тому пошук не був би миттєвим.
4. **Як зробити регістронезалежний пошук?** Запит перетворюємо через `query.trim().toLowerCase()`, назву — через `title.toLowerCase()`, а потім перевіряємо `includes(normalizedQuery)`. `trim()` прибирає лише пробіли по краях. Порожній рядок входить у кожну назву, тому очищений пошук повертає весь каталог.
5. **Чому reduce декларативний?** Він прямо описує зведення масиву до одного результату й тримає акумулятор усередині операції, зменшуючи потребу в зовнішній змінній та ручному індексі. Початкове значення `0` дає коректний результат для порожнього масиву. `for` також може бути цілком безпечним: reduce сам по собі не гарантує правильних чисел, валідації чи точності округлення.

## Лабораторна робота №14 — делегування подій і Drag-and-Drop

Картки реальних проєктів із GitHub API можна перетягувати в зону «Улюблені проєкти». Для портфоліо це адаптація зони улюблених товарів із методички. Зона показує назву та ID кожного проєкту й використовує той самий масив `selectedProjects`, що й кнопки, лічильник та модальне вікно. Повторне перетягування не створює дублікатів і не видаляє вже обраний проєкт. Стан зберігається до перезавантаження сторінки.

- Один обробник `click` на `.products-grid` використовує `event.target.closest(".btn-buy")` і працює з динамічними кнопками після Fetch.
- На картках є `draggable="true"` та `data-id`. На картинках і посиланнях вимкнено окреме перетягування.
- `dragstart` і `dragend` також делеговані контейнеру. `dataTransfer.setData("text/plain", id)` передає ID; клас `.dragging` зменшує непрозорість картки.
- `dragover` викликає `preventDefault()`, задає `dropEffect = "copy"` і підсвічує зону класом `.drag-over`; `dragleave` та `dragend` прибирають підсвічування.
- `drop` читає ID через `getData()`, перевіряє його за завантаженим масивом і активною карткою, додає проєкт та оновлює інтерфейс. Сторонні файли й текст не додаються до обраного.
- Кнопка «Обрати проєкт» залишається доступною для клавіатури й сенсорних екранів. Видалення та очищення в модальному вікні оновлюють також зону перетягування.

### Перевірка ЛР №14

1. Дочекатися завантаження проєктів, натиснути «Обрати проєкт»: назва й ID з'являються в зоні, лічильник збільшується.
2. Прибрати вибір та перетягнути картку за заголовок або вільне місце в зону «Улюблені проєкти»: картка стає напівпрозорою, зона підсвічується, після відпускання видно назву та ID.
3. Перетягнути той самий проєкт повторно: він залишається одним елементом, лічильник не збільшується.
4. Скасувати перетягування поза зоною: список не змінюється, підсвічування й прозорість скидаються.
5. Відкрити «Обране», прибрати проєкт або очистити список: зміни одночасно видно на картках і в зоні.
6. Перевірити вибір через Tab та Enter/Space, а також після повторного завантаження карток: окремі слухачі на нові кнопки не потрібні.

### Відповіді на контрольні питання ЛР №14

1. **Перевага делегування.** Один слухач на постійному батьківському контейнері обслуговує багато дочірніх елементів. Не потрібно додавати обробник на кожну кнопку або повторно прив'язувати його після динамічного створення карток; менше слухачів і простіший код.
2. **Роль `event.target`.** Це елемент, на якому виникла подія. Під час спливання подія доходить до контейнера, де через `event.target.closest()` знаходимо потрібну кнопку або картку, а з `dataset.id` отримуємо ID. `event.currentTarget` при цьому — контейнер зі слухачем. `closest()` враховує також клік по вкладеному елементу кнопки.
3. **Кнопки ще немає в DOM.** `document.querySelector()` поверне `null`. Спроба викликати `null.addEventListener()` спричинить `TypeError`. Навіть перевірка на `null` сама по собі не прив'яже слухач до майбутньої кнопки. Рішення — делегування на вже наявний контейнер або прив'язування після створення кнопки.
4. **`preventDefault()` у `dragover`.** За замовчуванням більшість елементів не приймають скидання. Скасування стандартної поведінки позначає зону як допустиму ціль, і браузер може виконати `drop`. Без цього скидання в нашій зоні не працюватиме.
5. **`event.dataTransfer`.** Зберігає дані та параметри поточного перетягування. У `dragstart` записуємо ID через `setData("text/plain", ...)`, а в `drop` читаємо його через `getData()`. Властивості `effectAllowed` і `dropEffect` описують дозволену й поточну дію. Прочитані дані перевіряємо перед використанням.

## Лабораторна робота №13 — інтеграція з публічним API

Поточна версія портфоліо завантажує до восьми публічних репозиторіїв автора через [GitHub REST API](https://docs.github.com/en/rest/repos/repos#list-repositories-for-a-user). Це адаптація завдання з FakeStoreAPI до особистого портфоліо: товари замінено проєктами, ціну — основною мовою, суму — кількістю унікальних обраних проєктів. Розділи нижче описують попередні лабораторні й історію розвитку сайту.

### Що реалізовано

- `fetchProjects()` виконує справжній GET-запит до `https://api.github.com/users/nikitauroboros-cpu/repos?type=owner&sort=updated&per_page=8` через `fetch()` та `async/await`.
- Перевіряється `response.ok`, JSON перетворюється через `await response.json()`. Локальний масив навичок та штучна двосекундна затримка більше не використовуються.
- Дані зберігаються у `globalStoreProjects`. Вибір шукає проєкт у цьому масиві через `find()`.
- Картки показують назву репозиторію, опис, основну мову, аватар автора й посилання на вихідний код. Відсутні описи та мови мають зрозумілі підписи.
- Працюють спінер, порожній стан, повідомлення про помилки HTTP/мережі/JSON, обмеження GitHub, 15-секундний тайм-аут і повтор завантаження.
- Модальне вікно ЛР №12, видалення, очищення та лічильник синхронізовані з обраними проєктами. Дублікати не створюються.
- Текст зовнішнього API екранується перед вставкою у HTML. Посилання дозволені лише через HTTPS на GitHub, аватари — з `avatars.githubusercontent.com`.

Публічні репозиторії GitHub можна читати без ключа. Анонімні запити мають ліміт; ключі або токени у клієнтському JavaScript не зберігаються. Кількість карток може бути меншою за вісім, якщо в автора менше публічних репозиторіїв. При перезавантаженні обране скидається, як у попередніх роботах.

### Як перевірити ЛР №13

1. Відкрити сайт через HTTP: у розділі «Мої проєкти» спочатку видно спінер, потім реальні репозиторії. У Network видно GET-запит до `api.github.com`, відповідь — JSON.
2. Перейти за посиланням «Переглянути на GitHub»: відкривається відповідний репозиторій.
3. Обрати проєкт, відкрити «Обране», прибрати його та очистити список. Лічильник, картки й модальне вікно мають оновлюватися.
4. У засобах розробника заблокувати запит до `api.github.com` і перезавантажити сторінку: спінер зникає, з'являються помилка й «Спробувати ще раз».
5. Зняти блокування та натиснути кнопку повтора: реальні картки знову завантажуються без оновлення всієї сторінки.

### Відповіді на контрольні питання ЛР №13

1. **HTTP та JSON.** HTTP — протокол обміну запитами й відповідями між клієнтом і сервером. JSON — текстовий формат даних. `fetch()` надсилає HTTP-запит, а сервер може повернути JSON у тілі HTTP-відповіді. `response.json()` читає це тіло й перетворює його на значення JavaScript.
2. **Неправильна адреса.** Непідтримувана схема на кшталт `htt://` або мережева помилка відхиляє Promise від `fetch()`. Помилку перехоплює `catch` у `fetchProjects()`, записує в консоль і передає далі через `throw`. `catch` у `initProjects()` показує повідомлення на сторінці, а `finally` прибирає спінер. Відповіді HTTP 404/500 самі по собі не відхиляють Promise: для них потрібна перевірка `response.ok`.
3. **Навіщо `response.json()`.** Сирий `Response` — об'єкт відповіді зі статусом, заголовками та потоком тіла, а не готовий масив. `await response.json()` асинхронно читає тіло й розбирає JSON у масив або об'єкт. `response.text()` повертає текстовий рядок, який довелося б окремо розбирати через `JSON.parse()`.
4. **Методи HTTP.** Крім GET, є POST — надсилання даних/створення ресурсу, PUT — заміна ресурсу, PATCH — часткове оновлення, DELETE — видалення, HEAD — отримання заголовків без тіла, OPTIONS — інформація про доступні можливості. GET є методом `fetch()` за замовчуванням; для іншого методу його явно задають у параметрах, наприклад `{ method: "POST" }`.
5. **Ключі API.** Ключ допомагає сервісу визначати клієнта, перевіряти доступ, рахувати запити й застосовувати квоти або оплату. Не кожен публічний API вимагає ключ. Навчальні GET-запити FakeStoreAPI та читання публічних репозиторіїв GitHub дозволені без нього, але мають власні обмеження. Секретні ключі не можна публікувати у відкритому коді сторінки.

## Лабораторна робота №11 — асинхронне завантаження

Картки навичок завантажуються з імітацією затримки відповіді сервера у 2 секунди. Функція `delay(ms)` використовує `Promise` і `setTimeout`, а `fetchSkills()` повертає масив після очікування. Поки дані завантажуються, видно спінер і текст «Завантаження навичок...». Далі `initSkills()` виводить картки через `map()` та `innerHTML`. Вибір навичок працює як раніше.

Помилки обробляються через `try...catch`, повідомлення виводиться через `textContent`. У `finally` спінер ховається і після успіху, і після помилки. Це навчальна симуляція: масив залишається у JavaScript, запиту до справжнього сервера для нього немає.

### Перевірка лабораторної №11

1. Відкрити `pages/index.html` через HTTP-сервер: спочатку видно спінер, приблизно через 2 секунди — 8 карток.
2. Обрати дві навички, прибрати одну та очистити обране — лічильник і список мають оновлюватися.
3. Відкрити `pages/index.html?loadError=1`: через 2 секунди замість карток з’явиться повідомлення про помилку, спінер зникне.
4. Прибрати `?loadError=1` з адреси і відкрити сторінку знову для звичайного завантаження.

### Контрольні питання

1. Синхронні операції виконуються послідовно. Асинхронне очікування не блокує решту JavaScript. Якби таймер блокував основний потік, сторінка під час очікування не реагувала б на взаємодію.
2. Стани Promise: `pending` — очікування, `fulfilled` — успіх, `rejected` — помилка. `resolve` передає результат і визначає подальший стан промісу, `reject` відхиляє його з причиною помилки.
3. `await` очікує результат промісу, призупиняючи поточну async-функцію, а не весь потік. Також він доступний на верхньому рівні JavaScript-модуля. `setTimeout()` повертає ідентифікатор таймера, тому для очікування його завершення потрібна обгортка у Promise.
4. `try...catch` дозволяє перехопити помилку очікуваного промісу й показати зрозуміле повідомлення користувачу.
5. Спінер приховує клас `.hidden` із властивістю `display: none !important`.

## Лабораторна робота №12 — модальне вікно обраних навичок

Завдання адаптоване до портфоліо та логіки ЛР №10: замість кошика товарів відкривається «Обрані навички». Масив `selectedSkills` містить унікальні навички, тому ціни та кнопки кількості «+»/«−» замінено рівнем навички, кнопкою «Прибрати» і загальною кількістю. Замість оформлення покупки — перехід до контактів.

- HTML: затемнення, діалог, заголовок, хрестик, список і підсумок.
- CSS: `position: fixed`, `z-index: 1000`, центрування через flex, прокручування довгого списку, плавна зміна прозорості.
- JS: відкриття через «Обране», закриття хрестиком, кліком по фону або Escape; актуальний список через `map()`, підсумок через `calculateTotal()`.
- Вибір, видалення й очищення синхронізують картки, лічильник, текстовий список і модалку.
- Діалог утримує фокус клавіатури, повертає його після закриття й блокує взаємодію з фоном.

### Перевірка ЛР №12

1. Відкрити головну через HTTP-сервер та натиснути «Обране»: порожній стан і підсумок 0.
2. Закрити вікно, обрати HTML та CSS, відкрити знову: дві навички з картинками й рівнями, підсумок 2.
3. Прибрати HTML у модалці: залишається CSS, підсумок і лічильник 1; картка HTML знову доступна для вибору.
4. Перевірити хрестик, Escape і клік по затемненню. Клік усередині білого вікна його не закриває.
5. Очистити обране: порожній список і підсумок 0. Перевірити Tab/Shift+Tab і вузький екран.

### Контрольні питання

1. `position: fixed` прив’язує оверлей до області перегляду, тому він залишається на екрані під час прокручування. `absolute` позиціонується відносно відповідного предка й може прокрутитися за межі екрана.
2. Порядком накладання керує `z-index` з урахуванням контекстів накладання.
3. `classList.toggle("hidden")` додає відсутній клас або прибирає наявний.
4. `event.target === cartOverlay` відрізняє клік по фону від кліку всередині діалогу. Без перевірки спливання події закривало б вікно також при натисканні на його вміст.
5. Спочатку змінюємо `opacity`, а після завершення CSS-переходу таймер додає `display: none` через `.hidden`. При відкритті спочатку знімаємо `.hidden`, фіксуємо початковий стан і додаємо клас видимості. `setTimeout` — функція, а не HTML-тег.
